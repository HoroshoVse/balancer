# Balancer

Balancer — это современный, высокопроизводительный балансировщик нагрузки (Load Balancer), написанный на Go (Backend) и React (Frontend).

## Основные возможности

- **TCP/UDP & HTTP балансировка:** Поддержка всех основных сетевых протоколов, включая HTTP/3 (QUIC) и TLS passthrough.
- **Продвинутая маршрутизация:** `Round Robin`, `Weighted Round Robin`, `Least Connections`, `IP Hash` и `Failover` (active-passive), ограничение соединений на узел (`max_conns`), резервные (backup) узлы: включаются все сразу или по одному в заданном порядке (порядок узлов меняется стрелками в редакторе).
- **Sticky Sessions:** по IP клиента (любой протокол) или по cookie (HTTP/HTTPS).
- **Health checks:** HTTP/HTTPS/TCP/UDP и настоящий DNS-запрос, свои интервал, таймаут и пороги срабатывания для каждого узла.
- **Auto SSL (Let's Encrypt):** Автоматический выпуск и продление SSL-сертификатов (ACME). Повреждённые файлы сертификата восстанавливаются сами, неудачный выпуск повторяется, о проблеме приходит уведомление.
- **Таймауты и переадресация:** таймаут подключения к узлу, простоя соединения и ответа узла; переадресация HTTP (порт 80) на HTTPS с обработкой проверок Let's Encrypt HTTP-01.
- **Prometheus Metrics:** Встроенный сбор метрик по адресу `/metrics` (RPS, Задержка, Ошибки).
- **Нагрузка на сервер:** на странице «Пульс» — графики процессора, памяти и сетевого интерфейса машины с балансировщиком за последние 5 минут (читаются из `/proc`, только Linux).
- **Telegram Уведомления:** Оповещения при падении и восстановлении узлов, переключении на резерв и проблемах с сертификатами (включая неудачное автопродление). В настройках есть кнопка «Отправить тестовое сообщение» — она сразу покажет, если неверен токен, не найден чат или сервер не достучался до Telegram; там же видно, дошло ли последнее уведомление.
- **Поддержка PROXY Protocol (v1/v2):** Прозрачная передача реальных IP-адресов клиентов на бекенды.
- **Инжект HTTP Заголовков:** Автоматическая установка `X-Real-IP`, `X-Forwarded-For` и `X-Forwarded-Proto`.
- **Фильтр по странам и спискам адресов:** кому можно подключаться, по странам по данным официальных регистраторов и по своим спискам IP и подсетей, с автоматическим обновлением баз и выгрузкой для файрвола.
- **Аутентификация & роли:** JWT, роли `Admin` / `Operator` / `Viewer`, защита от перебора паролей, CLI для управления пользователями.

## Установка

### Шаг 1. Docker
На Ubuntu 24.04 достаточно пакетов из стандартного репозитория:
```bash
sudo apt-get update
sudo apt-get install -y docker.io docker-compose-v2 git
sudo usermod -aG docker $USER
```
После этого перезайдите по SSH, чтобы `docker` работал без `sudo`. На других системах поставьте Docker Engine с плагином Compose по [официальной инструкции](https://docs.docker.com/engine/install/).

### Шаг 2. Скачивание конфигурации
```bash
git clone https://github.com/HoroshoVse/balancer.git
cd balancer
```

Пароль администратора можно задать сразу: раскомментируйте в `docker-compose.yml` строку `ADMIN_PASSWORD=` и впишите свой. Он применяется только при самом первом запуске, когда в базе ещё нет пользователей.

### Шаг 3. Запуск балансировщика

```bash
docker compose pull
docker compose up -d
```

### Шаг 4. Доступ к интерфейсу
Откройте в браузере: `http://<IP_вашего_сервера>:3000` и войдите как `admin`.

Если `ADMIN_PASSWORD` не задавали, пароль сгенерирован случайно и выведен один раз в лог бэкенда:
```bash
docker compose logs backend | grep "generated password"
```

Сменить его можно в любой момент, см. [Смена пароля администратора](#смена-пароля-администратора).

> API бэкенда слушает только `127.0.0.1:8080`, интерфейс обращается к нему через nginx фронтенда (`/api`). Наружу открыт только порт интерфейса `3000` и порты ваших балансировщиков. Интерфейс лучше дополнительно закрыть файрволом или VPN, если он не должен быть доступен из интернета.

### Переменные окружения (опционально)
Задаются в `docker-compose.yml`.

Бэкенд:
- `JWT_SECRET` — секрет подписи токенов (не короче 32 символов). Если не задан, генерируется случайный и сохраняется в БД.
- `ADMIN_PASSWORD` — пароль пользователя `admin` при первом запуске (когда в БД ещё нет пользователей).
- `API_ADDR` — адрес API (по умолчанию `127.0.0.1:8080`). `0.0.0.0:8080` откроет API наружу, например для Prometheus с другого хоста.
- `DB_DSN` — `postgres://...` для PostgreSQL или `sqlite:///app/data/balancer.db` для SQLite.

Фронтенд:
- `NGINX_PORT` — порт интерфейса (по умолчанию `3000`).
- `API_UPSTREAM` — куда nginx проксирует `/api` (по умолчанию `127.0.0.1:8080`).

### Обновление со старых версий
- Обновите `docker-compose.yml` (`git pull`): фронтенд теперь работает в `network_mode: host` и проксирует API, а бэкенд больше не открывает порт `8080` наружу.
- Если у вас остался пароль `admin/admin`, смените его: `docker compose exec backend ./balancer-cli users passwd admin <new_password>`. Пока пароль не сменён, бэкенд пишет предупреждение в лог.
- После обновления все пользователи один раз перелогиниваются (сменился секрет токенов).
- HTTPS-балансировщики раньше всегда ходили к узлам по HTTPS. Теперь это решает флаг узла «HTTPS», а для существующих HTTPS-балансировщиков он выставлен автоматически при миграции.

## DNS: AdGuard Home, Pi-hole и другие

- **Обычный DNS (порт 53).** Создайте балансировщик с протоколом UDP и включите галочку **«DNS server»**:
  - запросы идут через несколько постоянных сокетов к каждому узлу, ответ возвращается клиенту по DNS ID (нет сокета на каждый запрос, порты не заканчиваются под нагрузкой);
  - на том же порту работает TCP (клиенты переходят на него, если ответ не помещается в UDP);
  - узлы проверяются настоящим DNS-запросом (тип проверки «DNS query»). В поле «Query name» можно указать локальный домен (например, DNS rewrite в AdGuard), тогда проверка не зависит от upstream-серверов.
- **DoH.** HTTPS-балансировщик с терминацией SSL. Узлы: AdGuard `:443` с галочкой «HTTPS» или порт веб-интерфейса AdGuard без TLS, если в AdGuard включено `http.doh.insecure_enabled: true`. Для проверки узлов используйте HTTPS-путь `/` или «DNS query» на порт 53 (поле «Port» у проверки).
- **Почему лучше режим DNS, чем обычный UDP.** В обычном UDP на каждого клиента (новый адрес и порт) заводится отдельная сессия: сокет, поток и запись в таблице, и живёт она до окончания «простоя сессии» (по умолчанию 60 с). Тысячи «клиентов» в секунду, например при атаке со случайными портами, держат сотни мегабайт: на сервере с 1 ГБ это приводило к убийству процесса по нехватке памяти. Число таких сессий ограничено (16 384), лишние новые клиенты отбрасываются, об этом пишет журнал. Режим DNS сессий на клиентов не заводит вообще, и память не зависит от их числа.
- **DoT.** TCP-балансировщик на `853`, TLS проходит до узлов как есть.

Настройки на стороне AdGuard Home:
- `dns.ratelimit` (по умолчанию 20 запросов/с на клиента). За балансировщиком все клиенты выглядят для AdGuard одним IP, и лимит становится общим на всех. Поставьте `ratelimit: 0` или добавьте IP балансировщика в `ratelimit_whitelist`.
- Реальный IP клиента для DoH: добавьте IP (подсеть) балансировщика в `dns.trusted_proxies`, AdGuard возьмёт адрес из `X-Real-IP` / `X-Forwarded-For`. Для обычного DNS и DoT AdGuard видит IP балансировщика.
- PROXY protocol AdGuard Home не поддерживает (проверено на v0.107.79), не включайте его для узлов AdGuard.

## Xray / Marzban: VLESS, XHTTP и REALITY через IPv6-ноду

Схема «клиент → IPv4 балансировщика → IPv6 ноды» поддерживается: семейства адресов двух TCP-соединений могут отличаться. Для VLESS/XHTTP с REALITY используйте:

- протокол **TCP** или **HTTPS насквозь**, без расшифровки TLS на балансировщике;
- адрес ноды — IPv6, например `2001:db8::10`, порт отдельно, например `12006`. Вариант `[2001:db8::10]` тоже принимается; запись `[2001:db8::10]:12006` в поле адреса ошибочна;
- **«К узлу по TLS» выключено**: клиент уже отправляет REALITY/TLS, дополнительная TLS-обёртка меняет протокол;
- **PROXY protocol** включён только при включённом `streamSettings.sockopt.acceptProxyProtocol` у Xray. Передаваемые адреса описывают исходное клиентское соединение: для клиента по IPv4 это заголовок TCP4, даже если нода доступна по IPv6;
- на ноде Xray должен слушать нужный IPv6-адрес (`listen: "::"`), а порт должен быть разрешён в IPv6-файрволе и доступен именно с сервера балансировщика;
- если нод несколько, для режимов XHTTP с раздельными соединениями загрузки и скачивания используйте **«по IP клиента»** или закрепление по IP, чтобы соединения одной сессии попадали на одну ноду. При изменении набора доступных нод существующие сессии могут потребовать переподключения.

Открытие сайта маскировки не подтверждает работу VPN: REALITY умеет направлять неаутентифицированные подключения на сайт, а проверка UUID, ключей и XHTTP при этом не выполняется. Если IPv4 работает, а IPv6 нет, проверьте, что оба адреса ведут к одному Xray с одинаковыми пользователями и настройками REALITY (SNI, публичный ключ, short ID), а не просто к одинаковому сайту.

Кнопка проверки узла использует его адрес, SNI и настройки PROXY protocol балансировщика. Успех TCP означает только доступность порта; отправка PROXY-заголовка тоже не подтверждает, что Xray его принял. Обычная TLS-проверка не выполняет аутентификацию VLESS/REALITY. Проверять VPN нужно настоящим клиентом и по журналу Xray во время подключения.

Для сетевой диагностики выполните **на сервере балансировщика**, подставив настоящий IPv6:

```bash
ip -6 route get 2001:db8::10
nc -6 -vz -w 5 2001:db8::10 12006
docker compose logs --since=5m backend
```

`nc` проверяет только TCP: при `acceptProxyProtocol: true` нода может закрыть это подключение сразу после установления. Если порт доступен и сайт открывается, но VPN зависает на передаче данных, проверьте IPv6 MTU/PMTUD и прохождение ICMPv6 Packet Too Big на пути между балансировщиком и нодой; успешное подключение к порту этого не проверяет.

Документация Xray: [приём PROXY protocol](https://xtls.github.io/en/config/transports/sockopt.html), [XHTTP и его режимы](https://github.com/XTLS/Xray-core/discussions/4113), [REALITY](https://xtls.github.io/en/config/transports/reality.html).

### Как исключить балансировщик на рабочем сервере

В `diagnostics/haproxy-ipv6.cfg` есть независимый TCP-проброс через HAProxy: IPv4 на порту `12443` → IPv6 ноды на порту `12006`, с PROXY v2 и без обработки TLS. Замените `2001:db8::10` в этом файле настоящим адресом ноды. Затем из корня проекта **на том же Linux-сервере, где работает балансировщик**, запустите:

```bash
docker run --rm --name balancer-ipv6-check --network host \
  -v "$PWD/diagnostics/haproxy-ipv6.cfg:/usr/local/etc/haproxy/haproxy.cfg:ro" \
  haproxy:3.2-alpine
```

Сделайте копию рабочего клиентского профиля и поменяйте только порт подключения к IPv4 балансировщика на `12443`. UUID, SNI, публичный ключ REALITY, short ID, XHTTP path и режим должны остаться теми же. Порт `12443` должен быть свободен и доступен клиенту; основной сервис продолжит работать на своём порту. Завершение теста — `Ctrl+C` в терминале с HAProxy.

- **VPN работает через HAProxy, но не через Balancer:** сравнивайте настройки и версию Balancer, адрес/порт выбранной ноды, флаг дополнительного TLS и PROXY protocol.
- **VPN одинаково не работает через оба прокси:** сбой воспроизводится без Balancer; проверяйте Xray/Marzban, параметры профиля и IPv6-путь от этого сервера до ноды.
- **К тестовому порту вообще нет подключения:** сначала проверьте запуск HAProxy и доступ к порту; это ещё не результат проверки VPN.

HAProxy отправляет исходные адреса клиента в PROXY v2 согласно [официальной документации](https://docs.haproxy.org/3.2/configuration.html#send-proxy-v2). Этот контрольный тест не требует IPv6 на устройстве клиента и не меняет конфигурацию ноды.

## Доступ по странам и адресам

У каждого балансировщика можно ограничить, кто вправе подключаться (конструктор → «Кому можно подключаться»):

- **Только из выбранных стран** или **из всех, кроме выбранных**;
- **Всегда пускать** и **всегда блокировать** списки IP-адресов и подсетей. Они главнее стран и работают без выбора стран, например чтобы закрыть одну сеть-источник атаки;
- внутренние адреса (10.x, 172.16–31.x, 192.168.x, 100.64.x, 127.x, link-local) пускаются всегда, если их нет в списке блокировки.

Отказ мгновенный и без ответа: TCP и HTTPS-подключение закрывается сразу после приёма, до TLS и разбора запроса, UDP-пакет (в том числе DNS и QUIC) молча отбрасывается. Так сервер нельзя использовать для отражённых атак. Журнал вместо строки на каждый отказ раз в минуту пишет сводку («отсёк N подключений, чаще всего из: US ×820, HK ×310»), число отсечённых и страны видны на странице балансировщика.

**Кто обращается.** На странице балансировщика карточка «Кто обращается» показывает десять самых активных адресов за последние 10 минут: страну, сколько подключений или пакетов принято и сколько отклонено, и кнопку «Заблокировать» (добавляет адрес в список блокировки). Считается каждое TCP-подключение и каждый UDP-пакет, он же DNS-запрос, и у балансировщиков без правил доступа тоже. Так видно, кто шлёт трафик, даже когда узлы за балансировщиком видят только адрес самого балансировщика. Памяти уходит фиксированный объём: держатся самые активные адреса (около 256 на каждую минуту), поэтому поток с подменёнными случайными адресами её не раздувает, но при такой атаке цифры могут быть слегка занижены. Счётчики хранятся в памяти и обнуляются при перезапуске сервера; правка настроек балансировщика их не сбрасывает.

**Что спрашивали.** Для отказанных UDP-пакетов, похожих на DNS-запрос, в карточке «Фильтр доступа» показан список «Что спрашивали»: имя и тип запроса (TXT, ANY, A и так далее) за последние 10 минут. Поддомены сворачиваются до регистрируемого имени, поэтому атака с `xk3j9.example.com`, `q7zz1.example.com` и так далее видна одной строкой `example.com TXT`; для имён вида `foo.co.uk` остаётся `foo.co.uk`. Та же сводка (три самых частых имени) добавляется в минутную строку журнала об отказах. У TCP и DoH имени нет: подключение закрывается до того, как сервер прочитает запрос.

**Кто что спрашивал.** Кнопка «Что спрашивали» в карточке «Кто обращается» (у балансировщиков UDP и DNS) открывает окно: для каждого имени и типа запроса видно, сколько запросов прошло и сколько отклонено, а раскрыв имя, можно увидеть адреса, которые его спрашивали, с их страной, отметкой «проходит», «частично» или «отклоняется» и кнопкой «Заблокировать». Так видно, что именно просачивается через фильтр и откуда. Данные берутся с адреса, с которого пришёл пакет, то есть это настоящий клиент, а не балансировщик, которого видят узлы AdGuard. Для этого разбирается первый вопрос каждого UDP-пакета, в том числе принятого, без выделения памяти. Список адресов у имени ограничен восемью самыми активными, а запросы остальных показаны одной строкой. Окно запрашивает `GET /api/v1/load-balancers/queries?id=…`, остальные страницы нагрузки не увеличивает.

**Откуда берутся страны.** Из официальных файлов распределения адресов пяти региональных регистраторов: RIPE NCC, ARIN, APNIC, LACNIC и AFRINIC. Это первоисточник: они сами распределяют все публичные IP. Файлы качаются по HTTPS, проверяются по контрольной сумме, которую публикует тот же регистратор, и подменяются целиком и только после успешной проверки (при сбое остаётся прежняя версия). Другие источники не используются и адреса из настроек не принимаются.

- Первая загрузка занимает 5–15 минут (около 45 МБ, реестры отдают файлы медленно), потом данные обновляются сами раз в сутки (настраивается в «Настройки → Базы стран») и только пока хотя бы один балансировщик фильтрует по странам.
- **Пока база не загружена целиком, правила по странам пропускают всех** (иначе неудачная загрузка закрыла бы сервис для всех). Списки адресов работают всегда.
- Страна, которую знает регистратор, — это **страна регистрации сети**, а не обязательно физическое расположение сервера: сеть американской компании с серверами в Гонконге будет «US». Поэтому для защиты надёжнее режим «только из выбранных стран», чем «кроме выбранных». Адрес, которого нет ни в одном реестре, в режиме «только из выбранных» отклоняется.

Команды (из папки проекта):

```bash
docker compose exec backend ./balancer-cli geo status          # что загружено и насколько свежее
docker compose exec backend ./balancer-cli geo update          # скачать или обновить сейчас
docker compose exec backend ./balancer-cli geo lookup 8.8.8.8  # страна адреса
```

**То же в файрволе.** Файрвол отбрасывает пакеты в ядре и выдерживает поток куда больше, чем процесс в пользовательском пространстве. Те же проверенные списки можно выгрузить для `ipset` или `nftables` (формат `ipset` заменяет множества целиком и одним действием):

```bash
docker compose exec -T backend ./balancer-cli geo export RU,BY ipset geo_ok | sudo ipset restore
sudo iptables -I INPUT -p udp --dport 53 ! -i lo ! -s 10.0.0.0/8 -m set ! --match-set geo_ok src -j DROP
```

Для IPv6 те же шаги с `ip6tables` и множеством `geo_ok_v6`. Формат `nft` вместо `ipset` содержит и пример правила. Выгрузку надо повторять по расписанию (cron), иначе она устареет. Файлы базы лежат в `backend/data/geo`.

## 🛠 Управление пользователями (CLI)

В состав бэкенда входит встроенная утилита командной строки `balancer-cli`. Команды ниже выполняются на сервере из папки `balancer` (там, где лежит `docker-compose.yml`).

Роли: `Admin` — всё, включая настройки; `Operator` — управление балансировщиками; `Viewer` — только просмотр.

### Смена пароля администратора
**В интерфейсе:** «Настройки» → «Доступ» → «Сменить пароль». Нужны текущий пароль и новый, не короче 8 символов. Так свой пароль может сменить любой пользователь, в том числе с ролью `Viewer`.

**На сервере**, если пароль забыт или его нужно сменить другому пользователю:
```bash
docker compose exec backend ./balancer-cli users passwd admin <новый_пароль>
```
- Команда не спрашивает старый пароль.
- Чтобы пароль не остался в истории bash, начните строку с пробела.

После смены пароля любым способом все открытые сессии этого пользователя завершаются; при смене из интерфейса остаётся только та, из которой меняли. Неверный текущий пароль в форме считается неудачной попыткой входа: после 5 ошибок смена пароля и вход с этого адреса закрываются на 15 минут. Чтобы закрыть доступ совсем, удалите пользователя.

### Остальные команды

**Просмотр списка всех пользователей:**
```bash
docker compose exec backend ./balancer-cli users list
```

**Добавление нового пользователя:**
```bash
docker compose exec backend ./balancer-cli users add <username> <password> [role]
```

**Смена пароля:**
```bash
docker compose exec backend ./balancer-cli users passwd <username> <new_password>
```

**Смена роли и удаление:**
```bash
docker compose exec backend ./balancer-cli users role <username> <role>
docker compose exec backend ./balancer-cli users delete <username>
```

## Разработка

```bash
# Backend (нужен Go 1.22+); без DB_DSN используется локальный PostgreSQL
cd backend && DB_DSN=sqlite://balancer.db go run ./cmd/server

# Frontend: Vite проксирует /api на 127.0.0.1:8080
cd frontend && npm ci && npm run dev

# Проверки, которые запускает CI
cd backend && go vet ./... && go test ./...
cd frontend && npm run lint && npm run build
```

Дополнительные интеграционные проверки:

```bash
# Только отдельная временная PostgreSQL: тест создаёт пользователей и балансировщики.
cd backend
BALANCER_TEST_POSTGRES_DSN='postgres://test:test@127.0.0.1:5432/balancer_test?sslmode=disable' go test ./internal/api -run '^TestDeleteLoadBalancer$' -count=1

# Официальный бинарный файл Xray для той же ОС/архитектуры, IPv6 loopback должен работать.
BALANCER_TEST_XRAY=/path/to/xray go test ./internal/engine -run '^TestXrayXHTTPRealityIPv4ToIPv6$' -count=1 -v
```

Тест Xray использует локальные клиент и ноду с отдельными временными ключами: клиент подключается к IPv4 балансировщика, нода слушает IPv6 и требует PROXY protocol. Проверяются VLESS/XHTTP/REALITY, PROXY v1/v2, режимы `auto` и `packet-up`, загрузка и скачивание данных. Доступ к рабочей ноде не нужен; состояние IPv6-маршрута и настройки рабочего сервера этот тест не проверяет.

### Применение локальных изменений в Docker

Обычный `docker compose pull` загружает опубликованные образы и не включает изменения из вашей папки. Чтобы проверить локально изменённый код, соберите оба образа и пересоздайте сервисы (при этом активные подключения прервутся):

```bash
docker build -t ghcr.io/horoshovse/balancer-backend:latest ./backend
docker build -t ghcr.io/horoshovse/balancer-frontend:latest ./frontend
docker compose up -d --pull never backend frontend
```

Эти команды выполняются из корня проекта на сервере с нужными исходниками. PostgreSQL и её данные остаются на месте; удалять Docker volumes для применения исправления удаления не требуется.

## Общие списки IP и подсетей

В **Настройки → Доступ → Списки IP и подсетей** можно создать именованный список:

- Вписать IPv4, IPv6 и CIDR вручную или указать прямую публичную HTTP/HTTPS-ссылку на текстовый файл. Оба источника можно объединять. Для нескольких ссылок создайте несколько списков.
- По одному адресу или подсети в строке; также поддерживаются пробелы, запятые, точка с запятой, пустые строки и комментарии после `#`. Повторы удаляются, подсети приводятся к адресу сети. HTML, JSON, доменные имена и диапазоны через дефис не принимаются.
- Выбрать автообновление (по умолчанию раз в 24 часа) или обновлять вручную. Проверка расписания выполняется раз в минуту. До 200 000 записей и 8 МБ на список.

Затем в настройках балансировщика, в **Доступ по странам и адресам**, отметьте список в **Разрешённых списках** или **Запрещённых списках**. Один список можно использовать в нескольких балансировщиках. Разрешения имеют приоритет над блокировками и странами. Чтобы пускать только IP из списка, выберите **Только выбранные страны и разрешённые адреса**, оставьте страны пустыми и отметьте разрешённый список. Внутренние адреса по-прежнему пропускаются, если не заблокированы явно.

Обновление списка применяется к новым проверкам доступа без перезапуска слушателей и разрыва текущих соединений. При ошибке, некорректном или пустом ответе источника сохраняется последняя рабочая версия; состояние и время загрузки видны в настройках. Кэш хранится в БД и доступен после перезапуска. Смена ссылки требует успешной загрузки нового источника. Удаление используемого списка запрещено: сначала снимите его выбор в балансировщиках.

Списками управляют администраторы и операторы; наблюдатели могут их просматривать. Загрузка источников ограничена публичными адресами, включая адреса после перенаправлений.
